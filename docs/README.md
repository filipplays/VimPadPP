# Project knowledge

Start with the information relevant to the task; not every document needs to be
read for every change.

- [Project context](project-context.md): purpose, technology, constraints, and
  links to existing development documentation.
- [Architecture](architecture.md): components, integration paths, and testing
  boundaries.
- [Decisions](decisions/README.md): when and how to record significant
  architectural decisions.

The code and tests are evidence of current behavior. Existing build and test
documentation remains authoritative for its respective workflow. Check the
implementation when documentation may be stale, and distinguish verified facts
from proposals or uncertainties.

Keep documentation focused: update the relevant existing page when behavior
changes, and add a separate document only when it improves discovery or
maintenance. Preserve the history of decision records. Store personal
preferences or modify global instructions only with the user's approval, and
follow the user's explicit authorization requirements for all file changes.
